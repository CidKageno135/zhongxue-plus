## 3. Thử nghiệm Bác bỏ (Adversarial Probes) & Negative Controls Thực tế

R18 đã triển khai một bộ probe độc lập tại `tests/adversarial-r18-probe.test.ts` gồm 36 test cases, trực tiếp khởi tạo máy chủ TCP loopback thật (`RealTcpAppServer`, `FakeUpstreamServer`, `MockUpstreamServer`) và bắn các HTTP request đối kháng.

### 3.1. Nhóm F02: Thử nghiệm Đánh cắp Khóa liên Nhà cung cấp (Key Confusion)
1. **Ca probe 1.1 — Ép server nhả khóa AgentRouter sang OpenRouter:**
   - *Cách thử:* Gửi request chat tới `baseUrl: "https://openrouter.ai/api/v1"` không có `apiKey`, nhưng chỉ định `model: "gpt-6.1-sol"` (tên model đặc trưng của AgentRouter) kèm theo các header nội bộ của AgentRouter (`X-Provider: agentrouter`, `Originator: codex_cli_rs`).
   - *Kết quả đo được:* HTTP Status `400 Bad Request`. Toàn bộ response body hoàn toàn **KHÔNG** chứa sentinel key của AgentRouter (`SENTINEL_AGENTROUTER_KEY = 'sentinel-agentrouter-secret-key-11111'`). Upstream OpenRouter nhận 0 request.
2. **Ca probe 1.2 — Gửi model lạ/chưa từng thấy (`deepseek/deepseek-r1-zero:free`):**
   - *Kết quả đo được:* HTTP Status `400 Bad Request`. Khóa AgentRouter không bị rò rỉ.
3. **Ca probe 1.3 — Thử nghiệm qua action `ping`:**
   - *Cách thử:* Gửi ping tới OpenRouter không có `apiKey`.
   - *Kết quả đo được:* HTTP Status `400 Bad Request`, body `{ ok: false, error: ... }`. Không có request mang khóa bí mật nào thoát ra ngoài.
4. **Ca probe 1.4 & 1.5 — Môi trường Đa nhà cung cấp (Multi-provider isolation):**
   - *Kết quả đo được:* Khi client cung cấp `clientApiKey` riêng (`SENTINEL_CLIENT_KEY`), server chuyển tiếp đúng khóa này. Khi môi trường có cả 2 khóa, AgentRouter nhận đúng khóa AgentRouter, OpenRouter nhận đúng khóa OpenRouter.
5. **Negative Control F02:**
   - *Thử nghiệm âm:* Nếu server chỉ có khóa AgentRouter mà nhận request chỉ định OpenRouter, hàm `resolveUpstreamCredentials` lập tức trả về `isAllowed: false`, `apiKey: null`, `keySource: 'none'`. Chứng minh việc thiếu khóa nhà cung cấp tương ứng sẽ hủy bỏ quyền ủy quyền ngay lập tức.

### 3.2. Nhóm F03: Vector SSRF Mới, Encoded Fragment, Userinfo & Redirect 302
1. **Ca probe 2.1 — Các biến thể IPv6 Loopback:**
   - *Vector thử nghiệm:*
     - `http://[::1]:8080/v1`
     - `http://[0000:0000:0000:0000:0000:0000:0000:0001]:8080/v1`
     - `http://[::ffff:127.0.0.1]:8080/v1` (IPv4-mapped IPv6)
     - `http://[fe80::1]:8080/v1` (IPv6 Link-local)
     - `http://[fc00::1]:8080/v1` (IPv6 Unique Local)
   - *Kết quả đo được:* Trong chế độ mặc định production (`allowLocalDev: false`), **100% các vector trên đều bị từ chối** (`valid: false`, `error: Insecure protocol / SSRF protection`).
2. **Ca probe 2.2 — URL Encoded Fragments (`%23`):**
   - *Cách thử:* Gửi `baseUrl: "https://openrouter.ai/api/v1%23admin"`.
   - *Phân tích parser:* Theo đặc tả WHATWG URL, `%23` là ký tự literal nằm trong pathname (`/api/v1%23admin`), không phải dấu `#` phân tách fragment (hash vẫn là `""`). Do đó, `%23` không gây ra hiện tượng cắt ngắn URL (path truncation). Đồng thời, khi gửi qua HTTP thật không có client key, request vẫn bị chặn bởi chính sách F02 (HTTP 400).
3. **Ca probe 2.3 — Userinfo Injection:**
   - *Vector thử nghiệm:* `https://user:pass@agentrouter.org/v1`, `https://admin:secret@openrouter.ai/api/v1`, `https://admin@agentrouter.org/v1`, `http://attacker@localhost:8080/v1`.
   - *Kết quả đo được:* **100% bị từ chối** với thông báo lỗi `Forbidden userinfo: URLs containing username or password are not permitted`.
4. **Ca probe 2.4 — DNS Rebinding & Host Spoofing:**
   - *Vector thử nghiệm:* `http://127.0.0.1.nip.io/v1`, `http://localhost.evil.com/v1`, `http://agentrouter.org.attacker.com/v1`, `https://openrouter.ai.attacker.com/v1`.
   - *Kết quả đo được:* Toàn bộ giao thức `http:` từ xa bị chặn ngay lập tức. Tên miền giả mạo dưới giao thức `https:` bị đánh dấu `isTrusted: false` và không bao giờ được cấp khóa của server.
5. **Ca probe 2.5 — Upstream HTTP 302 Redirect sang Máy chủ Bẫy (Credential Leak Probe):**
   - *Cách thử:* Dựng một trap server lắng nghe trên cổng TCP loopback riêng (`http://127.0.0.1:<port>/sink`). Cấu hình mock upstream AI trả về HTTP 302 Redirect với header `Location: http://127.0.0.1:<port>/sink`. Gửi request chat mang Authorization header tới upstream.
   - *Kết quả đo được:* Do upstream fetch được cấu hình `redirect: 'manual'`, Node.js fetch **KHÔNG chạy theo redirect**. Trap server ghi nhận **nhận 0 request**, Authorization header **KHÔNG** bị rò rỉ. Server ứng dụng an toàn fallback về `mode: 'guided'`.
6. **Negative Control F03:**
   - *Thử nghiệm âm:* Gửi request với vector cắt path `http://127.0.0.1:<port>/admin-action#` tới máy chủ nội bộ. Kết quả: App server trả về HTTP 400 Bad Request, và máy chủ nội bộ ghi nhận **nhận 0 request**. Lỗ hổng SSRF path-truncation đã hoàn toàn bị triệt tiêu.

### 3.3. Nhóm F04: Kiểm định Vòng đời HTTP, Ngắt kết nối TCP và Ping Upstream
1. **Ca probe 3.1 — Client đóng kết nối TCP giữa chừng:**
   - *Cách thử:* Cấu hình upstream trễ 800ms để mô phỏng LLM sinh text chậm. Client gửi request POST `/api/conversation` rồi chủ động phá hủy socket TCP (`socket.destroy()`) sau 60ms.
   - *Kết quả đo được:* Mock upstream kích hoạt sự kiện `res.on('close')` và hàm `fakeUpstream.waitForAbort()` trả về `true` (nhận được tín hiệu ngắt sau 102ms). Server ứng dụng bắt êm sự kiện ngắt kết nối, không crash tiến trình, không in unhandled rejection.
2. **Ca probe 3.2 — Request bình thường không bị hủy nhầm:**
   - *Kết quả đo được:* Khi client giữ kết nối bình thường (upstream phản hồi sau 50ms), request trả về HTTP 200 với `mode: 'ai'` và nội dung đầy đủ; `wasAborted()` là `false`.
3. **Ca probe 3.3 — Đánh giá Tính kiên cường của Schema Ping Upstream:**
   - *Thử nghiệm 6 tình huống upstream phản hồi HTTP 200 nhưng nội dung bất thường:*
     1. Body rỗng 0 bytes (`""`): Server trả về `ok: false`, lỗi `empty or whitespace`.
     2. Body chỉ toàn khoảng trắng (`"   \n\t  "`): Server trả về `ok: false`, lỗi `empty or whitespace`.
     3. Body là JSON object rỗng (`{}`): Server trả về `ok: false`, lỗi `missing choices or output`.
     4. Body có mảng choices rỗng (`{ choices: [] }`): Server trả về `ok: false`, lỗi `missing choices or output`.
     5. Body chứa JSON lỗi (`{ error: { message: "Overloaded" } }`): Server trích xuất thông báo lỗi chính xác và trả về `ok: false`.
     6. Body trả về mã HTML (`<html>502 Bad Gateway</html>`): Server trả về `ok: false`, lỗi `not valid JSON`.
   - *Kết luận:* Đã loại bỏ hoàn toàn hiện tượng báo "sẵn sàng ảo" của upstream AI.

### 3.4. Nhóm F05: Validation Route Thật trên Live HTTP TCP
1. **Ca probe 4.1 đến 4.8 — Thử nghiệm Payload Bất thường:**
   - `POST "null"`: Trả về HTTP 400 Bad Request, code `BAD_REQUEST`.
   - `POST "true"`, `POST "123"`, `POST "\"hello\""`: Trả về HTTP 400 Bad Request.
   - `POST "[1, 2, 3]"` (JSON Array): Trả về HTTP 400 Bad Request.
   - `POST "{}"` (Object thiếu messages): Trả về HTTP 400 Bad Request (`messages array cannot be empty`).
   - `POST {"action":"chat","messages":[]}` (Mảng rỗng): Trả về HTTP 400 Bad Request.
   - `POST` với `Content-Type: text/plain` hoặc `application/x-www-form-urlencoded`: Trả về HTTP 415/400.
   - `POST` với payload vượt 100 KB: Trả về HTTP 413 Payload Too Large.
   - `POST` với role không hợp lệ (`role: "hacker"`): Trả về HTTP 400 Bad Request (`invalid message role`).
2. **Ca probe 4.9 & 4.10 — Phương thức HTTP:**
   - Các phương thức không được phép (`DELETE`, `PATCH`, `PUT`): Trả về HTTP 405 Method Not Allowed.
   - Phương thức probe `GET /api/conversation`: Trả về HTTP 200 OK trạng thái sẵn sàng (`status: 'ready'`).

### 3.5. Nhóm Static Security & Path Traversal Rebuttal
1. **Ca probe 5.1 & 5.2 — Directory Traversal:**
   - `GET /../../.env` -> HTTP 403 Forbidden.
   - `GET /%2e%2e/%2e%2e/.env` (URL-encoded) -> HTTP 403 Forbidden.
2. **Ca probe 5.3 & 5.4 — Tệp Cấu hình Nhạy cảm & Mã nguồn Backend:**
   - `GET /.env.example` -> HTTP 403 Forbidden.
   - `GET /package.json` -> HTTP 403 Forbidden.
   - `GET /server/index.ts` -> HTTP 403 Forbidden.
3. **Ca probe 5.5 — Null Byte Injection:**

4. **Ca probe 5.6 — Cách ly Endpoint API không tồn tại:**
   - `GET /api/nonexistent-action-endpoint` -> HTTP 404 Not Found với JSON envelope `{ error: { code: 'NOT_FOUND' } }`, hoàn toàn **KHÔNG** trả về mã HTML của SPA `index.html`.
