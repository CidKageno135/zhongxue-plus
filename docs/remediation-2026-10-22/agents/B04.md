## 1. Tóm Tắt Nguyên Nhân Gốc & Giải Pháp Kỹ Thuật

### 1.1. Invariant G4.1 — Bảo toàn Role & Lịch sử Hội thoại khi Chuyển Tab
- **Nguyên nhân gốc:**
  1. Trong baseline, `AiChatView.tsx` chỉ lưu tin nhắn vào `sessionStorage` qua key `zhongxue.draft.aichat.v1`, nhưng biến trạng thái `activeRole` lại được khởi tạo cứng thành `'free'` (`useState<string>('free')`).
  2. Khi người dùng chọn vai (ví dụ `🧋 Trà sữa (50嵐)` - roleId `'tea'`), gửi câu hỏi lượt 1, sau đó chuyển tab sang "Từ điển" rồi quay lại "Hội thoại", `AiChatView` bị unmount rồi remount.
  3. Khi remount, `messages` được khôi phục từ `sessionStorage`, nhưng `activeRole` bị reset ngược về `'free'`. Khi người dùng gõ tiếp lượt 2 và bấm gửi, payload gửi lên `POST /api/conversation` mang `roleId: 'free'` thay vì `'tea'`, vi phạm Invariant G4.1.
- **Giải pháp xử lý:**
  1. Thêm key lưu trữ chuyên dụng: `const AI_CHAT_ROLE_STORAGE_KEY = 'zhongxue.draft.aichat.role.v1'`.
  2. Xây dựng hàm `loadInitialRole()` đọc và kiểm tra tính hợp lệ của role lưu trữ trong `sessionStorage` so với danh mục `SCENARIO_ROLES`.
  3. Cập nhật `loadInitialMessages()` sử dụng role khởi tạo để hiển thị đúng lời chào chào mừng tương ứng thay vì luôn fallback về role đầu tiên.
  4. Bổ sung `useEffect` đồng bộ `activeRole` xuống `sessionStorage` và cập nhật `activeRoleRef`.
  5. Khi chuyển tab sang "Từ điển" rồi quay lại "Hội thoại", role `'tea'` cùng toàn bộ lịch sử tin nhắn lượt trước được phục hồi nguyên vẹn. Lượt gửi tiếp theo mang đúng `roleId: 'tea'` và mảng `messages` chứa đủ lịch sử turn 1 user, turn 1 assistant, và turn 2 user.

### 1.2. Invariant G4.2 — Cơ chế Generation Guard chống Race Condition khi Đổi Vai
- **Nguyên nhân gốc:**
  1. Trong baseline, khi một request A đang gửi tới backend (in-flight), nếu người dùng chuyển sang vai trò B (`switchRole`), hàm chỉ đơn thuần gọi `activeAbortControllerRef.current.abort()` và set `messages = [greetingMsg]`.
  2. Tuy nhiên, luồng bất đồng bộ của request A (bên trong `handleSend`) khi bị abort sẽ rơi vào khối `catch (err)`.
  3. Khối `catch (err)` của request A không có bất kỳ cơ chế nhận diện phiên nào (`requestId` / `generationId`). Do đó:
     - Nó lấy `lastDraftTextRef.current` của câu A điền ngược vào ô nhập liệu (`input`) của vai B.
     - Nó chèn thông báo hủy `⚠️ Yêu cầu đối thoại đã được hủy theo lệnh của bạn...` vào mảng `messages` của vai B.
     - Khối `finally` của A tắt cờ `loading = false`, vô tình dập tắt trạng thái đang chờ của request B nếu B đã được gửi ngay sau đó.
- **Giải pháp xử lý:**
  1. Thêm `generationIdRef = useRef<number>(0)` và `activeRoleRef = useRef<string>(activeRole)`.
  2. Mỗi khi người dùng chuyển vai (`switchRole`):
     - Tăng thế hệ request: `generationIdRef.current += 1`.
     - Hủy abort controller trước đó: `activeAbortControllerRef.current?.abort()`.
     - Xóa draft câu hỏi cũ: `lastDraftTextRef.current = ''`.
     - Cập nhật `activeRoleRef.current = role.id`.
     - Reset input rỗng và tắt loading.
  3. Trong `handleSend`:
     - Ghi nhận định danh phiên: `const thisRequestId = ++generationIdRef.current;` và `const thisRoleId = activeRoleRef.current;`.
     - Trong khối `try`, sau khi nhận được phản hồi AI:
       ```ts
       if (generationIdRef.current !== thisRequestId || activeRoleRef.current !== thisRoleId) {
           return; // Đã đổi vai hoặc có request mới hơn: loại bỏ phản hồi cũ
       }
       ```
     - Trong khối `catch`:
       ```ts
       if (generationIdRef.current !== thisRequestId || activeRoleRef.current !== thisRoleId) {
           return; // Tuyệt đối KHÔNG ghi đè tin nhắn hủy vào vai mới, KHÔNG leak draft vào input mới
       }
       ```
     - Trong khối `finally`:
       ```ts
       if (generationIdRef.current === thisRequestId && activeRoleRef.current === thisRoleId) {
           if (activeAbortControllerRef.current === controller) {
               activeAbortControllerRef.current = null;
           }
           setLoading(false);
       }
       ```
  4. Kết quả: Khi gửi Request A cho vai Trà sữa rồi ngay lập tức đổi sang vai Chợ đêm và gửi Request B, Request A bị loại bỏ sạch sẽ, không ghi đè bất kỳ tin nhắn hủy nào sang vai B, không làm ô nhập của B bị điền nhầm câu hỏi A, và loading của B được duy trì đến khi B phản hồi thành công `[ROLE_NIGHTMARKET_REPLY]`.

### 1.3. Invariant G4.3 — Hủy (Cancel) & Thử Lại (Retry) Sạch Sẽ, Loại Bỏ UI Notice
- **Nguyên nhân gốc:**
  1. Khi người dùng bấm "Hủy yêu cầu", hệ thống thêm một tin nhắn assistant mang nội dung thông báo UI: `⚠️ Yêu cầu đối thoại đã được hủy theo lệnh của bạn. Bạn có thể chỉnh sửa câu hỏi hoặc bấm "Thử lại".`.
  2. Khi người dùng chỉnh sửa câu hỏi và gửi lại, hàm `fetchConversationReply` lấy nguyên mảng `history` chuyển thành `turns` gửi lên `/api/conversation`.
  3. Tin nhắn assistant thông báo hủy UI bị gửi thẳng lên mô hình AI upstream, làm ô nhiễm ngữ cảnh học tập của mô hình và khiến acceptance test G4.3 đánh fail: `expect(cancellationTextInMessages).toBe(false)`.
  4. Khi người dùng bấm nút "Thử lại câu vừa hủy", `handleSend(retryText)` tiếp tục chèn thêm một lượt user turn mới có cùng nội dung với câu trước đó mà không dọn dẹp tin nhắn hủy cũ, gây trùng lặp lượt trò chuyện (duplicate user turn).
- **Giải pháp xử lý:**
  1. **Lọc sạch UI cancellation notices trong `fetchConversationReply`:**
     ```ts
     const isUiNotice = (content: string) =>
         content.includes('⚠️ Yêu cầu đối thoại đã được hủy') ||
         content.includes('hủy theo lệnh của bạn') ||
         content.includes('Đã hủy yêu cầu đối thoại');

     const turns: ConversationTurn[] = [];
     for (const m of history) {
         if (m.status === 'canceled' || m.status === 'error' || isUiNotice(m.content)) {
             continue; // Lọc bỏ hoàn toàn các tin nhắn trạng thái giao diện cục bộ
         }
         if (m.role === 'user' || m.role === 'assistant') {
             if (
                 m.role === 'user' &&
                 turns.length > 0 &&
                 turns[turns.length - 1].role === 'user' &&
                 turns[turns.length - 1].content === m.content
             ) {
                 continue; // Khử trùng lặp lượt user liên tiếp cùng nội dung
             }
             turns.push({ role: m.role, content: m.content });
         }
     }
     ```
  2. **Xử lý retry chuyên biệt (`handleRetry`):**
     - Khi bấm nút "Thử lại câu vừa hủy":
       ```ts
       const handleRetry = useCallback((msgId: string, retryText: string) => {
           const cur = messagesRef.current;
           const idx = cur.findIndex(m => m.id === msgId);
           const next = [...cur];
           if (idx !== -1) {
               next.splice(idx, 1);
               if (idx > 0 && next[idx - 1].role === 'user' && next[idx - 1].content === retryText) {
                   next.splice(idx - 1, 1);
               }
           }
           messagesRef.current = next;
           setMessages(next);
           void handleSend(retryText);
       }, [handleSend]);
       ```
     - Thu dọn sạch bong tin nhắn hủy và lượt user dang dở trước đó, chỉ giữ lại một lượt gửi duy nhất gửi lên backend.
  3. **Khử duplicate khi bấm Gửi trực tiếp từ input:**
     - Trong `handleSend`, nếu lượt gần nhất trước đó là một tin nhắn bị hủy có cùng nội dung với câu chuẩn bị gửi, hệ thống tự động loại bỏ cặp turn hủy dang dở để tránh nhân đôi turn trong hội thoại.
