## 1. Tóm Tắt Nguyên Nhân Gốc & Giải Pháp Kỹ Thuật

### 1.1. Lỗi F05 — Live Route Validation (`POST /api/conversation`) (Invariant G3)
- **Nguyên nhân gốc:**
  1. Trong baseline, `handleConversationRoute` (tại `server/ai.ts:518-534`) đọc trực tiếp request body thông qua stream thô rồi parse bằng `JSON.parse(raw || '{}')`.
  2. Không gọi qua hàm kiểm định `validateConversationBody` đã được định nghĩa trong `server/validation.ts`.
  3. Khi client gửi body là `"null"`, `JSON.parse("null")` trả về giá trị nguyên thủy `null`. Khi hàm `executeConversation` cố gắng truy cập `body.messages` hoặc `body.action`, Node.js văng ngoại lệ `TypeError: Cannot read properties of null (reading 'messages')`. Lỗi này không được bắt cục bộ, làm vỡ request và trả về HTTP 500 Internal Server Error thay vì HTTP 400 Bad Request.
  4. Khi client gửi `messages` sai định dạng (ví dụ `messages: "a-string"`, hoặc phần tử trong mảng thiếu `role`, hoặc `role: "super_admin"` không hợp lệ), do không có validation ở route POST thật, request rơi thẳng vào luồng fallback ngoại lệ và trả về HTTP 200 guided tutor, che giấu hoàn toàn lỗi vi phạm giao thức client.
  5. Không xác thực header `Content-Type: application/json` và không kiểm tra giới hạn kích thước payload `100KB` một cách chuẩn hóa bằng `HttpError(415)` và `HttpError(413)`.

- **Giải pháp xử lý tại `server/validation.ts` & `server/ai.ts`:**
  1. **Định nghĩa hằng số và hàm kiểm định tin nhắn chat trong `server/validation.ts`:**
     - Bổ sung `MAX_BODY_SIZE_CONVERSATION = 100 * 1024` (100 KB).
     - Bổ sung hàm `validateChatMessages(messages: unknown): ConversationTurn[]` kiểm tra nghiêm ngặt: `messages` phải là mảng, độ dài `<= MAX_MESSAGES_COUNT (50)`, mỗi phần tử phải là JSON object, `role` bắt buộc thuộc `VALID_MESSAGE_ROLES ('user', 'assistant', 'system')`, và `content` phải là chuỗi có độ dài `<= MAX_MESSAGE_CONTENT_LENGTH (4000)`.
     - Xuất alias `export const validateConversationRequest = validateConversationBody;`.
  2. **Nối validation vào `handleConversationRoute` (`server/ai.ts`):**
     - Kiểm tra header `Content-Type`: nếu có truyền mà không chứa `application/json`, gọi `validateJsonContentType` ném lỗi HTTP 415 `unsupportedMediaType`.
     - Đọc stream request có giới hạn `100KB`: kiểm tra cả `content-length` header khai báo trước và tổng số byte thực tế của các chunk stream; nếu vượt quá ném HTTP 413 `payloadTooLarge`.
     - Parse JSON an toàn bằng `parseJsonBody` và bọc trong khối bắt lỗi trả HTTP 400 `badRequest('Invalid JSON request body', undefined, 'BAD_REQUEST')`.
     - Gọi `validateConversationBody(rawBody)` để đảm bảo body bắt buộc phải là một JSON object hợp lệ (chặn `"null"`, mảng `[1, 2, 3]`, hoặc các kiểu nguyên thủy).
     - Kiểm tra bắt buộc đối với action `'chat'`: nếu `validBody.messages` rỗng, lập tức ném lỗi HTTP 400 `badRequest('messages array cannot be empty')`, ngăn chặn hoàn toàn việc trả 200 guided tutor để che lỗi client.

### 1.2. Lỗi F04 — Lifecycle, AbortSignal & Disconnect (`POST /api/conversation`) (Invariant G3)
- **Nguyên nhân gốc:**
  1. Trong baseline, `req.on('close', ...)` được đăng ký **sau khi** đã đọc xong toàn bộ stream body (`req.on('end')`). Trong mô hình stream của Node.js, khi request stream đọc tới EOF, `req` tự động kích hoạt sự kiện `close`. Do đó, listener được gán muộn không bao giờ bắt được sự kiện đóng kết nối sau đó.
  2. Quan trọng hơn, khi client chủ động hủy socket TCP trong lúc server đang chờ upstream AI phản hồi (sau khi đã gửi xong request body), sự kiện ngắt kết nối phía server được phát ra trên đối tượng `res` (`res.on('close')` khi `!res.writableEnded`), chứ không phải trên `req`. Baseline hoàn toàn không lắng nghe `res.on('close')`.
  3. Kết quả là khi client ngắt kết nối giữa chừng, `AbortController` của `fetch` tới upstream không bao giờ được kích hoạt `abort()`. Upstream server tiếp tục xử lý và giữ tài nguyên, gây lãng phí chi phí token/tính toán và rò rỉ socket descriptor.
  4. Khi upstream phản hồi sau khi socket đã đóng, server cố gắng ghi vào response đã kết thúc mà không kiểm tra cẩn thận trạng thái `res.writableEnded` và socket `destroyed`.
  5. Trong hàm `action === 'ping'`, baseline chỉ kiểm tra `if (pingRes.ok)` mà không đọc hoặc kiểm tra nội dung phản hồi của upstream. Khi upstream trả về HTTP 200 với body rỗng (0 bytes), body chỉ có khoảng trắng, hoặc body là JSON báo lỗi (`{ error: "Model overloaded" }`), baseline vẫn báo `ok: true`, gây sai lệch trạng thái sẵn sàng của mô hình AI.

- **Giải pháp xử lý tại `server/ai.ts` & `server/errors.ts`:**
  1. **Lắng nghe sự kiện ngắt kết nối sớm (Early Disconnect Lifecycle):**
     - Đăng ký listener ngay khi bắt đầu xử lý request:
       ```ts
       const clientController = new AbortController();
       const onClientDisconnect = () => {
         if (!res.writableEnded) {
           clientController.abort(new Error('CLIENT_CLOSED'));
         }
       };

       if (typeof res.on === 'function') {
         res.on('close', onClientDisconnect);
       }
       if (typeof req.on === 'function') {
         req.on('aborted', onClientDisconnect);
         req.on('close', () => {
           if (!req.complete && !res.writableEnded) {
             onClientDisconnect();
           }
         });
       }
       ```
     - Dọn dẹp listeners trong khối `finally` bằng `removeListener` để tránh rò rỉ bộ nhớ.
  2. **Hủy Upstream Request lập tức qua `AbortSignal`:**
     - Truyền `clientSignal: clientController.signal` vào `executeConversation`.
     - Trong `executeConversation`, đăng ký listener một lần (`once: true`) trên `clientSignal`: khi client ngắt, kích hoạt `controller.abort(new Error('CLIENT_ABORTED'))`, truyền trực tiếp vào `signal` của `fetchFn`.
     - Upstream AI provider (và fake upstream trong test) nhận được tín hiệu ngắt TCP ngay lập tức (`waitForAbort` trả về `true`).
  3. **Bảo vệ an toàn chống ghi vào response đã đóng (`server/errors.ts`):**
     - Cập nhật cả `sendJson` và `sendError`:
       ```ts
       if (res.writableEnded || ('destroyed' in res && (res as { destroyed?: boolean }).destroyed)) return;
       ```
     - Bọc `res.end()` trong `try/catch` để nuốt êm các lỗi socket write khi kết nối bị cắt đột ngột.
  4. **Kiểm định Schema & Nội dung Phản hồi Ping Upstream (`server/ai.ts`):**
     - Khi `pingRes.ok` là `true`:
       - Đọc chuỗi nội dung thô: nếu rỗng hoặc chỉ toàn khoảng trắng (`!rawPingBody || !rawPingBody.trim()`), trả về `ok: false` kèm thông báo lỗi rõ ràng.
       - Parse JSON nội dung thô: nếu không phải JSON hợp lệ hoặc không phải JSON object, trả về `ok: false`.
       - Kiểm tra xem upstream có trả về schema lỗi dạng `{ error: ... }` hay không: nếu có, trích xuất thông báo lỗi và trả về `ok: false`.
       - Xác thực cấu trúc chat completion / responses: kiểm tra sự tồn tại của mảng `choices` có phần tử, hoặc mảng `output`, hoặc trích xuất được `aiText`. Nếu thiếu, trả về `ok: false`.
       - Chỉ khi tất cả các kiểm định trên đều vượt qua, mới xác nhận `ok: true`.
